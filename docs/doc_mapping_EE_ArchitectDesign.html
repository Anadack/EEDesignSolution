Comment le framework transforme les pins logiques des systèmes en allocations ECU.

Vue d’ensemble du mapping

Objectif

Router chaque signal de système vers une pin ECU compatible

Le mapping parcourt les composants d’un système, leurs capteurs, actionneurs, pins et signaux, puis cherche une ressource ECU libre et compatible.

Sortie attendue

Signal mappé + ECU pin occupé

Quand le mapping réussit, pin.connected_signal pointe vers le signal, signal.is_mapped = true, et la pin est marqué occupé.

Cas particulier

GROUND peut recevoir plusieurs connexions

Les pins ground sont marqués occupés mais restent acceptables pour d’autres connexions afin de supporter une topologie étoile.

La compatibilité de rôle est la première barrière de mapping.

Règle fondamentale : rôle logique ↔ rôle ECU

Le framework considère la pin du device comme une vue logique côté système, et la pin ECU comme une ressource physique côté contrôleur. La relation est volontairement inversée pour les capteurs et actionneurs.

Pin logique systèmeInterprétationPin ECU attenduRésultat

INOUTBus bidirectionnel, typiquement CAN/LIN/ETHINOUTOK
SUPPLYAlimentation deviceSUPPLYOK
GROUNDRetour masseGROUNDOK
UNASSIGNEDNC/DNC ou pin catalogue non mappableTout rôleToléré
Autre combinaisonIncohérence de direction—Rejeté
Localisation code : EEC_connect.c:72-93 et règle miroir dans EEC_verify.c:74-94.
Un rôle compatible ne suffit pas : la pin ECU doit aussi supporter l’interface du signal.

Compatibilité interface et capacité ECU

Après la vérification du rôle, le framework convertit l’interface du signal en masque de capacité ECU puis vérifie que la pin physique expose cette capacité.

Exemples d’interfaces signal

  • DIGITAL
  • ANALOG
  • PWM
  • CAN
  • LIN
  • SENT
  • ETHERNET
  • RESISTANCE
  • FREQUENCY
  • CURRENT
  • POWER
  • GROUND

Conditions générales

  1. Le signal existe.
  2. La pin ECU existe.
  3. La pin ECU n’est pas occupé, sauf ground.
  4. Le masque interface du signal est non nul.
  5. La pin ECU supporte cette capacité.
Pin occupé ?Oui, et pas GROUND → rejet
Interface compatible ?Non → rejet
GROUND occupé ?Accepté, multi-connexion étoile
Localisation code : EEC_architecture.c:791-803 pour EEC_Ecu_IsPinCompatible(), puis EEC_architecture.c:805-825 pour EEC_Ecu_ConnectSignalToPin().
Les deux champs utilisent le même bitmask mais n’ont pas le même sens.

Electrical capability / electrical requirement

electrical_capability décrit ce que la pin ECU physique sait fournir ou mesurer. electrical_requirement décrit ce que la pin logique du device exige pour être correctement connectée. Le principe de compatibilité est : toutes les exigences bloquantes du device doivent être couvertes par les capacités de la pin ECU candidate.

Règle mentale : electrical_requirement & ~electrical_capability doit être égal à zéro pour un matching totalement propre. Si des bits manquent, le mapping strict rejette ou signale l’incompatibilité ; la vérification peut aussi produire un warning selon la criticité et le type de bit manquant.

Différence capability vs requirement

electrical_capability=68 sur une pin ECU signifie que cette pin fournit HIGH_SIDE + VOLTAGE_IN. electrical_requirement=4 sur une pin device signifie que le device exige seulement HIGH_SIDE. Le mapping est OK car 4 est inclus dans 68.

Ces options définissent l’état électrique par défaut d’une entrée.

Comment fonctionnent pull-up et pull-down

Pull-up

Une résistance interne tire le signal vers une tension haute. Si le capteur ou l’interrupteur est ouvert, la lecture reste à 1 ou à une tension connue. Si le capteur ferme vers la masse, l’entrée passe à 0.

ECU +5V ─ resistor ─ input pin ─ switch/sensor ─ GND
Open  → high
Closed → low

Pull-down

Une résistance interne tire le signal vers la masse. Si le capteur est ouvert, la lecture reste à 0. Si le capteur force la ligne vers une tension haute, l’entrée passe à 1.

VBAT/+5V ─ switch/sensor ─ input pin ─ resistor ─ GND
Open  → low
Closed → high

Dans les JSON, digital_structure peut indiquer PULLUP ou PULLDOWN. Si le device exige réellement cette polarisation, le bit correspondant doit aussi apparaître dans electrical_requirement. La pin ECU candidate doit alors posséder le bit dans electrical_capability.

CasRésultat attendu
digital_structure=PULLUP + electrical_requirement=1, pin ECU capability contient 1OK
digital_structure=PULLUP + requirement 1, capability ne contient pas 1Rejet strict ou warning de vérification selon la fonction appelée.
digital_structure=UNSPECIFIED, requirement 0OK si rôle et interface sont compatibles.

Choisir vers quel ECU mapper un ou plusieurs systèmes

Le framework permet déjà de cibler un ECU, mais principalement par le code appelant. La liste ecus[] passée à la fonction est utilisée dans l’ordre fourni. Si tu passes un seul ECU, le système ne peut se mapper que sur ce ECU.

Mapper un système sur un ECU précis

EEC_Ecu_t *rear_only[] = { rear_ecu };
EEC_StrictConnectPolicy_t policy = { NULL, 0U, true, true, true };

int mapped = EEC_System_connect_to_ecus_strict(
    hydraulic_system,
    rear_only,
    1U,
    &policy,
    trace
);

Si aucune pin compatible n’existe sur rear_ecu, le système ne sera pas déplacé vers un autre ECU.

Préférer un ECU, avec fallback

EEC_Ecu_t *preferred[] = { rear_ecu, central_ecu, cab_ecu };
EEC_StrictConnectPolicy_t policy = { NULL, 0U, true, false, true };

int mapped = EEC_System_connect_to_ecus_strict(
    hydraulic_system,
    preferred,
    3U,
    &policy,
    trace
);

Le premier ECU trouvé avec une allocation réussie peut devenir préféré si prefer_same_ecu est actif.

Stratégie pratique par zones tracteur

/* 1) Systèmes hydrauliques forcés sur Rear ECU */
EEC_Ecu_t *rear_ecu_set[] = { rear_ecu };
EEC_System_connect_to_ecus_strict(hydraulic, rear_ecu_set, 1U, &hard_policy, trace);

/* 2) Systèmes cabine préférés sur Cab ECU puis Central ECU */
EEC_Ecu_t *cab_set[] = { cab_ecu, central_ecu };
EEC_System_connect_to_ecus_strict(cab_hmi, cab_set, 2U, &prefer_policy, trace);

/* 3) Le reste en AutoMapSmart sur les ressources restantes */
EEC_Ecu_t *remaining[] = { front_ecu, central_ecu, rear_ecu };
EEC_Architecture_AutoMapSmart(arch, remaining, 3U, trace);
Limite actuelle : le modèle JSON ne contient pas encore une politique déclarative complète comme target_ecus, preferred_ecus, forbidden_ecus. C’est une amélioration recommandée pour industrialiser ce comportement.
Simple, rapide, mais moins contraignant.

Mode relaxed : premier pin compatible

Le mode relaxed parcourt les pins device non mappés, puis les ECU et leurs pins dans l’ordre fourni. Dès qu’il trouve une pin compatible, il connecte le signal et passe au signal suivant.

1. Ignorer la pin si pas de signal ou signal déjà mappé.
2. Parcourir chaque ECU dans l’ordre fourni.
3. Parcourir chaque pin ECU.
4. Vérifier rôle logique ↔ rôle ECU.
5. Vérifier compatibilité interface/capacité.
6. Émettre un warning si AgPL requis supérieur au pin, mais continuer.
7. Connecter le premier pin accepté.
[AUTO] RearHitchPosition → REAR_ECU X2/14
[AUTO-WARN] SafetyPressure requires AgPL D but REAR_ECU X1/9 supports C
Important : en relaxed, l’AgPL insuffisant produit un warning dans la trace, mais ne bloque pas forcément le mapping.
Le mode strict sélectionne le meilleur candidat parmi les pins compatibles.

Mode strict : filtres + scoring

Filtres bloquants

  • Rôle incompatible.
  • Interface/capacité incompatible.
  • AgPL de la pin inférieur à l’AgPL requis.
  • Connecteur différent si preferred_connector est imposé.
  • Fonction de pin absente si required_pin_function est imposé.
  • Diagnostics manquants si required_diagnostic_flags est imposé.

Scoring appliqué

  • +1000 si ECU préféré par prefer_same_ecu.
  • +300 connecteur préféré.
  • +200 fonction requise présente.
  • +100 signal critique, +60 haut, +30 moyen.
  • +50 safety-related, +40 si diagnostic disponible.
  • +80 si les exigences électriques sont pleinement satisfaites.
  • -25 par bit électrique manquant.
  • +10 si pin physique ≤ 16.
Comportement de rejet : si aucune pin ne passe les filtres, le mapping du signal échoue. Si require_all_signals=true, la fonction stricte retourne -1 dès qu’un signal obligatoire ne peut pas être connecté.
[STRICT] RaiseValvePWM → REAR_ECU X4/8
[STRICT] FAIL SteeringAngle_SENT
La fonction EEC_System_MapToEcu est la plus directe pour cibler un ECU.

AutoMapSmart : ordre de priorité des systèmes

EEC_Architecture_AutoMapSmart() ne réordonne pas les ECU, mais réordonne les systèmes. L’ordre des ECU reste celui fourni par l’appelant.

+20000Système mandatory
+take_rate × 100Take rate véhicule
+8000/+6000/+4000/+2000Priority CRITICAL/HIGH/MEDIUM/LOW
+AgPL × 2500Sécurité requise
+SL × 1500Niveau système SL4..SL1
+diversité × 500Nombre de types d’interface distincts
+pin_count × 2Systèmes volumineux mappés plus tôt
Usage recommandé : mapper manuellement les systèmes critiques/zone-spécifiques sur leurs ECU cibles, puis lancer AutoMapSmart pour le reste.

Règles de vérification appliquées après mapping

V-rules : ECU + logical pins

V1Détection CAN address dupliquée globalement.
V2Pin occupé avec signal, signal sur pin occupé.
V3Unicité connector+physical_number sur chaque ECU.
V4Paires différentielles CAN/ETH adjacentes et même connecteur.
V5Tous les signaux logiques sont mappés.
V6Pas de signal affecté à plusieurs pins ECU.
V7Compatibilité de rôles device ↔ ECU.
V8Matching capability électrique.
V9Pull-up / pull-down requis.
V10Couverture diagnostics.
V11Nominal/inrush current vs current_max.
V12Pas de mélange GND_POWER/GND_LOGIC.
V13Safety signal sur pin avec diagnostics.

B-rules : Bus

B1Index de port valide pour capacité ECU.
B2Un même ECU+port n’est pas partagé par plusieurs bus.
B3Interface du signal compatible avec le type de bus.
B4Pas de doublon ECU+port sur le même bus.
B5CAN/ISOBUS ≤ 32 nodes : warning si dépassement.
B6Adresses CAN uniques sur le bus.
B7Les signaux bus sont affectés à un bus : warning sinon.
B8Bitrate > 0 si nodes connectés : warning sinon.
Nuance : le résumé du code initialise un compteur warnings, mais plusieurs warnings sont imprimés directement sans incrémenter systématiquement ce compteur. Il faut donc lire le texte du rapport, pas seulement le nombre global de warnings.

Exemples pratiques

Cas OK — capteur analogique

Un capteur position produit une sortie analogique.

Device pin: role=OUTPUT, interface=ANALOG
ECU pin:    role=INPUT,  capability=ANALOG
Result:     MAP OK → ECU ADC input

Cas OK — bobine high-side

Une électrovanne reçoit une commande depuis ECU.

Device pin: role=INPUT, interface=PWM,
            electrical_requirement=HIGH_SIDE
ECU pin:    role=OUTPUT, capability=PWM,
            electrical_capability=HIGH_SIDE
Result:     MAP OK → PWM_HS output

Warning — AgPL relaxed

Le mapping relaxed avertit si la pin ne supporte pas le niveau safety requis.

[AUTO-WARN] SteeringAngle requires AgPL D
but FRONT_ECU X2/7 supports C
[AUTO] SteeringAngle -> FRONT_ECU X2/7

Rejet — SENT sur pin analog

L’interface du signal ne correspond pas à la capacité de la pin.

Device signal: interface=SENT
ECU pin:       supported_capability=ANALOG
Result:        no compatible free pin / FAIL

Erreur vérification — masse mélangée

Un actionneur de puissance ne doit pas partager une masse logic/signal.

Device pin ground_class=POWER
ECU pin ground_class=LOGIC
Verify: ERROR ground class mismatch

Erreur bus — pas de paire différentielle

CAN/ETH doit avoir une paire adjacente de même interface sur le même connecteur.

CAN_H mapped at X1/10
No adjacent CAN pin at X1/9 or X1/11
Verify: ERROR differential pairing issue
