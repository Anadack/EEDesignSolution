Git workflow guide for a tractor E/E JSON library repository

This guide defines the recommended Git workflow for a repository containing tractor JSON assets: tractor definitions, system-of-systems, systems, components, sensors, actuators, ECUs, configurations, mapping policies and generated documentation.

The objective: every JSON change must be reviewable, traceable, validated by CI, owned by the right domain expert, and released with confidence.

2. Standard Git workflow Recommended

Use a PR-based GitHub Flow: short-lived branches, mandatory validation, mandatory review, squash merge, protected main.

Golden rule

The source of truth is the reviewed JSON library content in main, plus the schemas and validation rules used to approve it. Generated HTML reports are release artifacts, not the source of truth.

3. Branching model

main

Protected branch. Must always contain validated JSON, passing CI and releasable content.

feature/<domain>-<short-name>

Used for new systems, components, sensors, actuators, ECUs and configurations.

fix/<domain>-<issue>

Used for correcting JSON fields, mapping rules, connector metadata, or validation errors.

Recommended branch names

feature/hydraulic-rear-hitch-premium
feature/ecu-rear-chassis-controller
feature/sensor-hydac-hda8400-pressure
fix/connector-din-pin-count
fix/mapping-policy-rear-hitch
docs/json-contract-update
Avoid long-lived integration branches unless a release train is really required. Short-lived PR branches keep JSON ownership and validation easier.

5. JSON validation pipeline Required

Every pull request must pass validation before it can be merged.

V1
JSON syntaxEvery *.json file must parse successfully. No invalid JSON, trailing commas or bad encodings.
V2
Schema validationEach JSON is validated against its declared schema, for example system.schema.json, sensor.schema.json, ecu.schema.json.
V3
Naming conventionFile name, name, id and object type must be consistent.
V4
Pin / signal consistencyEach mappable pin must have a signal, role, interface and I/O classification.
V5
Connector consistencyused_cavities must not exceed total_cavities, cavities must be unique, and connector names must be stable.
V6
Electrical compatibilityElectrical requirement values must be supported by ECU electrical capability values.
V7
Mapping policy checksTarget ECU names, preferred ECU lists, forbidden ECU lists and exclusive groups must reference existing objects.
V8
I/O sizing checksThe pipeline generates an I/O matrix and verifies one-active-at-time groups using max-per-I/O-type rules.
V9
Report generationHTML documentation and CSV/JSON summaries must be generated without errors.

Required CI status checks

validate-json-syntax

Blocks malformed JSON.

validate-schemas

Blocks invalid object contracts.

validate-library-consistency

Blocks broken references, pin/signal mismatch and bad mapping policy.

6. Pull request rules

PR must explain intent

What tractor/platform/system is changed? Is it a new system, ECU, sensor, actuator, mapping policy, or configuration?

PR must include validation result

Include local validation output or the CI summary. JSON changes without validation are not mergeable.

PR must identify impact

Does it change I/O needs, mapping behavior, ECU pins, safety, diagnostics, or generated reports?

PR must have owner approval

At least one domain owner must approve. Schema and validation changes require validation owner approval.

Merge rules

  • Use squash merge for feature/fix branches.
  • Do not merge if any required CI job fails.
  • Do not bypass review for JSON changes affecting safety, electrical requirements, ECU capabilities, or connector pinouts.
  • Every merged PR should leave main in a releasable state.

7. Release workflow

Use controlled tags for library releases consumed by the framework or downstream tools.

R1
Freeze release candidateCreate release/vYYYY.MM.N or tag directly from validated main if using pure GitHub Flow.
R2
Run full validationSchema, consistency, I/O sizing, generated HTML reports and manifest checks must pass.
R3
Generate artifactsCreate generated reports, manifest, checksum and release notes.
R4
Create tagUse vYYYY.MM.N, for example v2026.06.1.
R5
Publish GitHub releaseAttach generated package, validation report and release notes.

9. Ready-to-use examples

GitHub Actions workflow

name: Validate JSON Library

on:
  pull_request:
    branches: [ main ]
    paths:
      - '**/*.json'
      - 'schemas/**'
      - 'tools/**'
      - '.github/workflows/validate-json.yml'
  push:
    branches: [ main ]

jobs:
  validate:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with:
          python-version: '3.11'
      - run: python -m pip install --upgrade pip jsonschema
      - run: python tools/validate_json_syntax.py .
      - run: python tools/validate_json_schemas.py --root . --schemas schemas
      - run: python tools/validate_repo.py --root .
      - run: python tools/generate_io_matrix.py --root . --input systems --out generated/io_sizing/system_io_matrix.csv
      - run: python tools/generate_html_docs.py --root . --out generated/html/index.html

10. Checklists

Before opening a PR
  • Run JSON syntax validation locally.
  • Run schema validation locally.
  • Generate the I/O matrix.
  • Open generated HTML and inspect the changed system.
  • Check that system alternatives use max_per_io_type when only one is active at a time.
Before approving a PR
  • Confirm that the correct owner reviewed the changed domain.
  • Verify safety, diagnostics and electrical requirement changes.
  • Verify connector cavities, pin roles and signal definitions.
  • Verify target/preferred ECU mapping policy if present.
  • Check CI artifacts and generated reports.
Before release
  • All CI checks are green on main.
  • Manifest generated and reviewed.
  • Release notes generated.
  • Generated HTML documentation attached or published.
  • Tag created from the validated commit.
Common rejection reasons
  • Malformed JSON.
  • Missing schema version or wrong object type.
  • Pin count and signal count mismatch.
  • Unknown ECU, component, sensor or actuator reference.
  • Electrical requirement not supported by ECU capability.
  • Exclusive group incorrectly summed instead of max-sized.
