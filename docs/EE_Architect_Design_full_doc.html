1. Mental model

The framework models a tractor E/E architecture as a hierarchy of systems, components, devices, pins, signals, ECUs and buses. Mapping is the operation that connects logical device signals to physical ECU pins.

ArchitectureTop-level container
SystemFunction / option / platform feature
ComponentFunctional grouping
DeviceSensor or actuator
Pin + SignalPhysical endpoint + logical data

Logical architecture

Systems, components, sensors, actuators and signals. This answers: what does the machine feature need?

Physical architecture

ECUs, connectors, pin cavities, capabilities, diagnostics and buses. This answers: where can it be connected?

Mapping layer

Compatibility, scoring, validation and trace. This answers: is this assignment electrically and functionally valid?

3. Build and run workflow

A typical workflow compiles the C framework, runs an example architecture, writes JSON exports, then launches documentation scripts.

# Example build idea from a project root
make clean
make strict-compile
make run

# Typical exports expected by documentation tools
generated_doc/exports/example_architecture.json
generated_doc/exports/example_physical_architecture.json

# Generate reports or viewers
python tools/scripts/generate_all_architecture_docs.py --root .
python tools/scripts/generate_system_configuration_viewer_html.py --root . --input library/systems --verbose
Portability rule. Prefer configurable compiler/tool paths. Avoid hard-coded Windows-only paths inside wrapper scripts.

4. Create a first architecture

The smallest useful model contains an architecture, one system, one signal, one sensor or actuator, and one ECU with a compatible pin.

#include "EEC_architecture.h"
#include "EEC_connect.h"
#include "EEC_verify.h"
#include "EEC_export.h"

int main(void) {
    EEC_Architecture_t *arch = EEC_Architecture_Create("Demo Tractor Architecture");

    EEC_System_t *hyd = EEC_Architecture_CreateSystem(arch, "Hydraulic Position Control");
    hyd->priority = EEC_PRIORITY_HIGH;
    hyd->safety = EEC_SAFETY_QM;
    hyd->system_level = EEC_SYSTEM_LEVEL_SL2;
    hyd->is_mandatory = true;
    hyd->take_rate = 100.0f;

    EEC_Component_t *cmp = EEC_System_CreateComponent(hyd, "Rear Hitch Position Sensor Assembly");
    EEC_Sensor_t *sensor = EEC_Component_CreateSensor(cmp, "Rear Hitch Position Sensor");

    EEC_Signal_t *pos = EEC_Architecture_CreateSignalEx(
        arch, "RearHitchPosition", EEC_SIGNAL_TYPE_UNSIGNED_16BIT,
        EEC_SIGNAL_INTERFACE_ANALOG, EEC_SIGNAL_UNIT_PERCENT,
        0.0f, 100.0f, 0.1f, 1.0f);

    EEC_Sensor_CreatePin(sensor, 1, EEC_PIN_ROLE_OUTPUT, pos,
                         EEC_PIN_INTERFACE_ANALOG, "Position output");

    EEC_Ecu_t *ecu = EEC_Architecture_CreateEcu(arch, "Rear ECU", "MEDIUM");
    EEC_Ecu_CreatePin(ecu, 12, "X1", "AI_12", "ANALOG_INPUT",
                      EEC_PIN_ROLE_INPUT, EEC_PIN_INTERFACE_ANALOG,
                      EEC_Signal_InterfaceToCapability(EEC_SIGNAL_INTERFACE_ANALOG),
                      EEC_DIAG_RANGE_CHECK,
                      "0-5V analog input", "ADC");

    EEC_Ecu_t *ecus[] = { ecu };
    EEC_System_connect_to_ecus(hyd, ecus, 1, stdout);
    EEC_Verify_architecture(arch, stdout);
    EEC_Export_architecture_json(arch, "generated_doc/exports/example_architecture.json");
    EEC_Export_physical_architecture_json(arch, "generated_doc/exports/example_physical_architecture.json");

    EEC_Architecture_Destroy(arch);
    return 0;
}

7. Electrical capabilities, requirements, roles and pull resistors

Electrical capability belongs to an ECU pin: what the pin can provide. Electrical requirement belongs to a device pin or signal: what the device needs. Mapping is safe only when hard requirements are covered.

Electrical bitmask values

HexSymbolMeaning
0x00EEC_ELEC_NONENo special electrical feature required/provided.
0x01EEC_ELEC_PULLUPInternal pull-up. The pin biases a floating switch/signal to logic high when the external contact is open.
0x02EEC_ELEC_PULLDOWNInternal pull-down. The pin biases a floating switch/signal to logic low when the external contact is open.
0x04EEC_ELEC_HIGH_SIDEHigh-side driver. ECU sources current from VBAT/supply to the load.
0x08EEC_ELEC_LOW_SIDELow-side driver. ECU sinks current from the load to ground.
0x10EEC_ELEC_PUSH_PULLPush-pull output stage. ECU can actively drive high and low.
0x20EEC_ELEC_CURRENT_SENSECurrent measurement or current-loop capability, for example 4–20 mA.
0x40EEC_ELEC_VOLTAGE_INHigh-impedance voltage measurement input.
0x80EEC_ELEC_DIFFERENTIALDifferential signaling pair, for example CAN_H/CAN_L or Ethernet pair.

Roles

RoleMeaningTypical mapping
INPUTDevice pin consumes a command/supply? On ECU side, INPUT means ECU reads the signal.Sensor OUTPUT usually maps to ECU INPUT.
OUTPUTDevice pin produces a value or ECU pin drives a signal.Actuator INPUT usually maps to ECU OUTPUT.
INOUTBidirectional communication.CAN/LIN/Ethernet-like channels.
SUPPLYPower/reference supply.ECU SUPPLY pin provides VBAT/5V/8.5V/10V to device SUPPLY pin.
GROUNDGround/return.Ground class must match: POWER versus LOGIC when specified.
UNASSIGNEDCatalog-only / NC / DNC / intentionally unused.Should not be mapped automatically.

ANALOGVoltage analog signal.AI + VOLTAGE_IN capability

SENTSENT sensor channel.SENT input

Requirement rule. For hard electrical matching: (ecu_pin.electrical_capability & device_pin.electrical_requirement) == device_pin.electrical_requirement.

How pull-up and pull-down work

Pull-up

The ECU biases the input toward logic high through an internal resistor. A switch to ground pulls the input low when closed. Useful for active-low switches and open-collector/open-drain outputs.

Pull-down

The ECU biases the input toward logic low. A switch to supply pulls the input high when closed. Useful for active-high switches and floating signal prevention.

// Example: digital input that requires a pull-up
signal->digital_structure = EEC_DIGITAL_STRUCTURE_PULLUP;
device_pin->electrical_requirement |= EEC_ELEC_PULLUP;

// ECU candidate must provide the pull-up capability
ecu_pin->electrical_capability |= EEC_ELEC_PULLUP;

Mapping assigns each logical device pin/signal to a physical ECU pin. The framework has relaxed, strict, single-ECU and architecture-level strategies.

FunctionWhen to useBehavior
EEC_System_MapToEcu(system, ecu, trace)You want one system on one target ECU.Searches only that ECU. Compatible pins are used; failures are reported as mapping failures.
EEC_System_connect_to_ecus(system, ecus, count, trace)You have a list of allowed ECUs.Uses ECUs in caller-provided order and maps to first compatible free pin.
EEC_System_connect_to_ecus_strict(system, ecus, count, policy, trace)You need connector/function/diagnostics constraints.Filters and scores candidates using strict policy and can fail if required signals cannot be mapped.
EEC_Architecture_AutoMapAll(arch, ecus, count, trace)Simple architecture-level mapping.Loops through unmapped systems and maps them using relaxed mapping.
EEC_Architecture_AutoMapSmart(arch, ecus, count, trace)Best default for complex architectures.Sorts systems by score: mandatory, take rate, priority, AgPL, system level, interface diversity, pin count.

Targeting selected ECUs

// Map hydraulic system only on Rear ECU
EEC_Ecu_t *rear_only[] = { rear_ecu };

9. Strict mapping policy

Strict mapping adds per-signal rules and scoring. It is suitable for safety-relevant signals, diagnostic requirements and connector constraints.

EEC_StrictSignalRule_t rules[] = {
    {
        .signal_name = "RearHitchPosition_A",
        .preferred_connector = "X1",
        .required_pin_function = "ANALOG_INPUT",
        .required_diagnostic_flags = EEC_DIAG_RANGE_CHECK | EEC_DIAG_PLAUSIBILITY
    }
};

EEC_StrictConnectPolicy_t policy = {
    .rules = rules,
    .rule_count = sizeof(rules)/sizeof(rules[0]),
    .prefer_same_ecu = true,
    .require_all_signals = true,
    .verbose_trace = true
};
Strict filter/scoring elementEffect
Role + interface compatibilityHard filter. Candidate is skipped if incompatible.
AgPL supportHard filter in strict mode when candidate cannot support required AgPL.
Preferred connectorHard filter when specified, and positive score when matched.
Required pin functionHard filter when specified.
Required diagnosticsHard filter when specified.
PriorityHigher priority signal increases score.
Diagnostic richnessPins with diagnostic flags score better.
Electrical matchPins covering all electrical requirements score better; missing bits are penalized or rejected by hard mapping.
Prefer same ECUFirst successful ECU receives a strong bonus for subsequent mappings.

10. Verification rules

Verification runs after mapping to detect hard errors and warnings. It should be part of every build or release pipeline.

Architecture rules V1–V13

RuleNameWhen it fails or warns
V1Duplicate CAN address detectionERROR if two ECU objects use the same CAN node address.
V2ECU pin occupied/signal consistencyERROR if occupied pin has no signal or signal attached to a non-occupied pin.
V3ECU pin identity uniquenessERROR if same ECU connector/physical pin is defined more than once.
V4Differential pair validationERROR if CAN/ETH/LIN differential interfaces miss expected adjacent pair structure.
V5Signal-to-ECU mapping completenessERROR if a logical signal referenced by a device pin is not mapped when expected.
V6Duplicate signal assignmentERROR if one signal is assigned to multiple ECU pins, except accepted shared ground cases.
V7Role compatibilityERROR for role mismatch between device pin and ECU pin.
V8Electrical capability matchingWARNING or ERROR depending missing capability; requirement must be subset of capability for hard requirements.
V9Pull resistor requirementERROR when mandatory pull-up/pull-down is required but ECU pin lacks capability.
V10Diagnostics coverageERROR if required diagnostics are not covered by ECU diagnostic flags.
V11Current overloadERROR for nominal overload; WARNING for high inrush edge cases.
V12Ground class mixingERROR if POWER ground device is routed to LOGIC ground or inverse mismatch when classes are specified.
V13Safety diagnostic coverageERROR when a safety-relevant signal has no diagnostic capability.

Bus rules B1–B8

RuleNameWhen it fails or warns
B1ECU bus port availabilityERROR when requested port index exceeds available ports.
B2Port exclusivityERROR when one ECU port is connected to multiple buses.
B3Duplicate ECU+port on busERROR for repeated bus nodes.
B4Bus/signal interface compatibilityERROR if CAN bus carries non-CAN-compatible signal, etc.
B5CAN node countWARNING when CAN nodes exceed practical limit such as 32.
B6Duplicate CAN address on busERROR for duplicate addresses on same network.
B7Bitrate missingWARNING if bus bitrate is zero while nodes are connected.
B8Unassigned bus signalWARNING when a bus-capable signal is not assigned to any bus.

15. Best practices

Modeling

  • Use explicit pins: one connector cavity = one device pin = one mappable signal/net.
  • Represent NC/DNC as UNASSIGNED and non-mappable.
  • Use stable Ref-2X, part numbers and schema versions.

Mapping

  • Use strict mapping for safety-relevant systems.
  • Order ECU candidate arrays deliberately.
  • Use one target ECU list for dedicated systems and SmartMap for the rest.

Electrical

  • Always set electrical requirements for actuator drivers.
  • Use ground classes to avoid logic/power ground mixing.
  • Define diagnostics requirements for safety-relevant pins.

Documentation

  • Generate architecture docs after every mapping change.
  • Archive HTML, CSV and JSON summaries together.
  • Keep generated docs standalone for easy design review.

16. Troubleshooting

SymptomLikely causeFix
Signal not mappedNo free compatible ECU pin, wrong role, wrong interface, or missing capability.Check trace lines, ECU pin capability mask, role and interface.
Electrical mismatch warningDevice requirement not fully provided by ECU capability.Add correct capability to ECU pin or change device topology.
Pull resistor errorDigital signal requires pull-up/down but candidate pin lacks it.Set ECU pin EEC_ELEC_PULLUP or EEC_ELEC_PULLDOWN.
Ground class errorPOWER ground device routed to LOGIC ground or inverse mismatch.Use correct ground class or create dedicated power/signal ground pins.
Diagnostics gapDevice requires diagnostics unavailable on the ECU pin.Choose diagnostic-capable pin or lower requirement only if justified.
CAN duplicate addressTwo ECUs share same CAN node address.Assign unique addresses per network.
System viewer I/O count looks too highUsing cumulative mode while systems are alternatives.Switch to Alternatives mode: one active system at a time.
